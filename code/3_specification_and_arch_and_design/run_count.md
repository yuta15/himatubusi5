# 非同期ジョブ実行エンジン 追加仕様 v1.2 — 最大同時実行数制限

## 1. 概要

既存の非同期ジョブ実行エンジンに、同時に実行できるジョブ数を制限する機能を追加する。

実行数が上限に達している場合も、ジョブの登録は受け付ける。登録されたジョブは実行可能になるまで `PENDING` 状態で待機する。

v1.0およびv1.1の機能・公開契約は、本仕様に明記した変更点を除き維持すること。

## 2. 公開インターフェース

### エンジン生成

`main.py` の `create_engine()` に最大同時実行数を指定できる引数を追加する。

```python
def create_engine(max_concurrency: int | None = None) -> JobEngine:
    ...
```

- `max_concurrency` は同時に実行できるジョブ数の上限を表す。
- 正の整数を指定できる。
- `None` は同時実行数の制限なしを意味する。
- 引数を省略した場合は `None` として扱う。
- `0`、負数、整数以外の値は `ValueError` または `TypeError` で拒否する。
- `bool` は整数として扱わず、無効な指定とする。
- 上限はエンジン生成時に確定し、実行中の変更は対象外とする。

既存の `JobEngine` の各メソッド、および `JobStatus` と例外クラスの公開定義は変更しない。

## 3. ジョブの登録

- `submit()` は実行中のジョブ数にかかわらず、新しいジョブを登録できる。
- 登録時には従来どおり一意なジョブIDを返す。
- 同時実行数が上限に達していても、`submit()` は実行枠が空くまで待機してはならない。
- 実行可能になるまで待機しているジョブは `PENDING` 状態とする。
- 登録済みジョブの情報は、実行待機中も参照できること。

## 4. 同時実行数の制御

- 同一エンジン内で、`RUNNING` 状態のジョブ数が `max_concurrency` を超えてはならない。
- 実行枠に空きがある場合、`PENDING` のジョブを実行できる。
- 実行開始時に `PENDING → RUNNING` へ遷移する。
- 実行枠がない場合、ジョブの処理本体を開始してはならない。
- 実行中のジョブが終端状態に到達すると、そのジョブが使用していた実行枠を解放する。
- 空き枠が生じ、実行待機中のジョブがある場合は、新たな登録操作を必要とせず、自動的に実行を進めること。
- ジョブが失敗またはキャンセルされた場合も実行枠を解放する。
- 実行待機中のジョブが存在し、実行枠が利用可能である場合、他のジョブが無期限に待機しない限り、待機中ジョブの実行が進行できること。

実行数の上限は、ジョブの処理本体が実行中である数に適用する。内部的に生成される非同期Taskの数は制限対象としない。

## 5. 実行順序

- 登録されたジョブの実行順序は保証しない。
- FIFO、優先度、その他のスケジューリング方式は指定しない。
- 実行順序にかかわらず、登録済みジョブが実行可能な状態で不当に放置されないこと。
- 同じジョブの処理本体が重複して実行されてはならない。

## 6. ジョブの状態管理

既存の状態は変更しない。

- `PENDING`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`

以下を満たすこと。

- 実行待機中のジョブは `PENDING` を維持する。
- 実行枠を確保して処理本体を開始すると `RUNNING` に遷移する。
- 実行結果に応じて `SUCCEEDED`、`FAILED`、`CANCELLED` のいずれかに遷移する。
- 終端状態に到達したジョブは再実行しない。
- 終端状態は変更されない。

## 7. キャンセルとの連携

v1.1のキャンセル仕様を維持し、実行待機中のジョブについて以下を追加する。

### PENDINGジョブのキャンセル

- 実行待機中のジョブに対して `cancel()` を呼び出せる。
- 初回のキャンセル要求は `True` を返す。
- キャンセルされたジョブの処理本体は実行されない。
- キャンセルが完了すると `CANCELLED` となる。
- キャンセルしたジョブを後から実行してはならない。
- PENDINGジョブのキャンセルによって、他のジョブの実行を妨げてはならない。

### RUNNINGジョブのキャンセル

- RUNNINGジョブのキャンセルはv1.1の仕様に従う。
- キャンセル要求を受け付けただけでは実行枠を解放してはならない。
- ジョブの実際の終了が確定した時点で実行枠を解放する。
- キャンセルを抑制して処理が継続する場合も、実行中は実行枠を占有する。

## 8. 完了待機と結果取得

既存の `wait()`、`get_status()`、`get_result()` の契約を維持する。

- PENDINGジョブに対する `wait()` は、そのジョブが終端状態になるまで待機する。
- PENDINGジョブに対する `get_result()` は、待機せず `JobNotFinishedError` を送出する。
- PENDINGジョブに対する `get_status()` は `JobStatus.PENDING` を返す。
- RUNNINGおよび終端状態の振る舞いは従来どおりとする。
- あるジョブへの完了待機が、別のジョブの実行開始を妨げてはならない。

## 9. エンジン間の独立性

- 最大同時実行数はエンジンインスタンスごとに適用する。
- 異なるエンジン間で実行枠を共有しない。
- 一方のエンジンが上限に達していても、別のエンジンの実行を妨げない。

## 10. 非機能要件

### 並行性

- 最大同時実行数を超過しないこと。
- 実行待機によってイベントループをブロックしないこと。
- 非同期処理の実行中に、他の実行可能なジョブが進行できること。
- CPU処理の並列高速化は保証しない。

### データ保持

- 実行待機中のジョブも、登録済みジョブとして管理すること。
- 終端状態に到達したジョブの状態および結果は、エンジン稼働中に参照できること。

### 互換性

- `max_concurrency` を省略した場合、既存の無制限実行と互換性を維持すること。
- v1.0およびv1.1の既存の公開APIの振る舞いを維持すること。

## 11. 受け入れ条件

- [ ] 最大同時実行数を指定してエンジンを生成できる。
- [ ] 無効な最大同時実行数を拒否できる。
- [ ] 上限に達していても新しいジョブを登録できる。
- [ ] 実行待機中のジョブが `PENDING` を維持する。
- [ ] 実行中のジョブ数が指定上限を超えない。
- [ ] 実行枠が空くと待機中ジョブが自動的に実行される。
- [ ] 正常終了・異常終了・キャンセル後に実行枠が解放される。
- [ ] 実行待機中のジョブをキャンセルできる。
- [ ] キャンセルしたPENDINGジョブの処理本体が実行されない。
- [ ] RUNNINGジョブへのキャンセル要求だけでは実行枠が解放されない。
- [ ] キャンセルを抑制したジョブは実行が終了するまで実行枠を占有する。
- [ ] PENDINGジョブの状態照会・結果取得・完了待機が正しく動作する。
- [ ] エンジンごとに独立した実行数制限が適用される。
- [ ] 制限なしのエンジンで従来の並行実行が維持される。
- [ ] 既存のv1.0およびv1.1の契約テストが引き続き合格する。

## 12. 実装上の自由度

以下の実装方法は指定しない。

- Queue、Semaphore、実行中ジョブ集合などのデータ構造
- スケジューリング方式
- 実行枠の取得・解放方法
- ジョブと実行制御コンポーネントの関係
- クラスやメソッドの追加・変更
- 内部Taskの生成・保持方法
- ジョブの実行順序

ただし、すべての公開契約と受け入れ条件を満たすこと。
