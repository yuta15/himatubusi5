# 非同期ジョブ実行エンジン 追加仕様 v2.0

## 1. 概要

既存の非同期ジョブ実行エンジンに、以下の機能を追加する。

- リトライ
- 指数バックオフ
- タイムアウト
- ジョブ間の依存関係（DAG）
- 優先度付きスケジューリング

追加機能は、既存のキャンセル機能および最大同時実行数制限と組み合わせて利用できること。

v1.0〜v1.2の公開契約は、本仕様で明示的に拡張する部分を除き維持する。

本仕様は公開インターフェースと外部から観測可能な振る舞いを定義する。内部アーキテクチャおよび実装方法は指定しない。

## 2. 公開インターフェース

### 2.1 追加する公開型

`interface.py` に以下を追加する。

```python
from dataclasses import dataclass, field
from typing import Awaitable, Callable


@dataclass(frozen=True)
class RetryPolicy:
    max_retries: int = 0
    initial_delay: float = 0.0
    multiplier: float = 2.0
    max_delay: float | None = None
    retry_on: tuple[type[Exception], ...] = (Exception,)


@dataclass(frozen=True)
class JobSpec:
    func: Callable[..., Awaitable[object]]
    args: tuple[object, ...] = ()
    kwargs: dict[str, object] = field(default_factory=dict)
    retry: RetryPolicy = field(default_factory=RetryPolicy)
    timeout: float | None = None
    priority: int = 0
    depends_on: tuple[str, ...] = ()
```

### 2.2 追加するメソッド

`JobEngine` に以下を追加する。

```python
async def submit_job(self, spec: JobSpec) -> str:
    ...
```

- 指定された設定でジョブを登録し、一意のジョブIDを返す。
- ジョブの開始や完了を待たずに返る。
- 無効な設定は登録時に拒否する。
- 登録失敗時は不完全なジョブを残さない。
- 登録時点の設定を使用し、登録後の呼び出し元による設定変更の影響を受けない。

### 2.3 追加する例外

```python
class JobDependencyError(JobError):
    def __init__(self, dependency_id: str):
        self.dependency_id = dependency_id
        super().__init__(
            f"Dependency job did not succeed: {dependency_id}"
        )
```

依存関係の不成立でジョブが `FAILED` となった場合、`get_result()` は `JobExecutionError` を送出する。その `cause` は `JobDependencyError` とし、`dependency_id` に失敗した直接の依存ジョブIDを保持する。

### 2.4 既存APIとの互換性

既存の `submit()`、`get_status()`、`wait()`、`get_result()`、`cancel()` はシグネチャを変更しない。

既存の `submit()` で登録したジョブは、リトライなし・タイムアウトなし・依存関係なし・優先度0として動作する。

`create_engine(max_concurrency: int | None = None)` も変更しない。

## 3. リトライ

ジョブの実行が失敗した場合、指定された条件に応じて再実行できること。

- `max_retries` は初回実行を除いた追加試行回数とする。
- `max_retries=2` の場合、最大3回実行する。
- `retry_on` に指定された例外型またはそのサブクラスで失敗した場合のみリトライする。
- リトライ対象外の例外では直ちに `FAILED` となる。
- 正常終了した場合は `SUCCEEDED` となり、追加試行しない。
- すべての試行が失敗した場合は `FAILED` とし、最後の例外オブジェクトを `JobExecutionError.cause` に保持する。
- 各試行では登録されたCallableを新たに呼び出す。
- 同一ジョブの複数試行が同時に実行されてはならない。
- `asyncio.CancelledError` は通常のリトライ対象としない。

`max_retries` は0以上の整数とし、`bool` は拒否する。

`retry_on` は `Exception` のサブクラスからなる空でない `tuple` とする。

## 4. 指数バックオフ

リトライまでの待機時間を指数的に増加させられること。

n回目のリトライ前の待機時間は、次の式に従う。

```python
delay = initial_delay * multiplier ** (n - 1)
if max_delay is not None:
    delay = min(delay, max_delay)
```

nは1から開始する。

- `initial_delay` は0以上の有限数値とする。
- `multiplier` は1以上の有限数値とする。
- `max_delay` は `None` または0以上の有限数値とする。
- 無効な設定値を拒否する。
- 待機処理はイベントループをブロックしない。
- バックオフ中はジョブの状態を `PENDING` とする。
- バックオフ中は同時実行数制限の実行枠を占有しない。
- 待機終了後、実行可能になったジョブは再度スケジューリングされる。
- バックオフ中にキャンセルされたジョブは、以降の試行を実行しない。

個々の試行が失敗しても、リトライが残っている限りジョブ全体を `FAILED` として確定してはならない。

## 5. タイムアウト

ジョブの実行時間に上限を設定できること。

- `timeout` は秒単位とし、正の有限数値または `None` を指定する。
- `None` はタイムアウトなしとする。
- タイムアウトはリトライの各試行に適用する。
- 実行枠・依存関係・バックオフの待機時間は計測対象に含めない。
- タイムアウト時は実行中の処理に協調的な中断を要求する。
- 中断要求を送信しただけではジョブを終了済みとして扱わない。
- 処理が実際に終了するまで実行枠を保持する。

タイムアウトにより処理が `asyncio.CancelledError` で終了した場合、その試行を `TimeoutError` による失敗として扱う。

`TimeoutError` がリトライ条件に一致する場合、残りの試行回数に応じてリトライする。リトライしない場合は `FAILED` となり、`JobExecutionError.cause` に `TimeoutError` を保持する。

ただし、処理が中断要求を捕捉して正常終了した場合は成功とし、別の例外で終了した場合はその例外を失敗原因とする。

タイムアウトは強制終了を保証しない。

## 6. ジョブ間の依存関係（DAG）

ジョブ登録時に、先行ジョブへの依存関係を指定できること。

- `depends_on` には同一エンジン内の登録済みジョブIDを指定する。
- 複数の依存先を指定できる。
- すべての依存先が `SUCCEEDED` になるまで、後続ジョブの処理本体を実行しない。
- 依存関係待機中は `PENDING` とし、実行枠を占有しない。
- 依存先がすべて成功すると、後続ジョブは自動的に実行可能となる。
- 依存先の結果を後続ジョブの引数に自動的に渡す必要はない。

### 6.1 依存関係の検証

- 存在しない依存先は `JobNotFoundError` とする。
- 依存先IDの重複指定は `ValueError` とする。
- 登録後の依存関係変更は認めない。
- 未登録ジョブへの前方参照は認めない。

### 6.2 依存ジョブの失敗

依存先が最終的に `FAILED` または `CANCELLED` になった場合、後続ジョブは本体を実行せず `FAILED` となる。

- `JobExecutionError.cause` に `JobDependencyError` を保持する。
- 複数の依存先が失敗した場合、どの直接依存先を原因として報告するかは指定しない。
- 失敗は依存関係に沿って後続ジョブへ伝播する。
- 依存関係のないジョブには影響しない。
- 先行ジョブがリトライ中の場合、その最終結果が確定するまで後続は待機する。
- 依存関係待機中のジョブを直接キャンセルした場合は、既存のキャンセル契約に従い `CANCELLED` とする。

## 7. 優先度付きスケジューリング

ジョブに優先度を指定できること。

- `priority` は整数とし、`bool` は拒否する。
- デフォルトは0とする。
- 数値が大きいほど優先度が高い。
- 依存関係やバックオフの待機条件を満たしたジョブを実行可能とする。
- 実行枠が空いた時点で実行可能な複数ジョブが存在する場合、優先度が高いジョブから実行する。
- 同じ優先度の場合、実行可能になった順序で実行する。
- 同時に実行可能となった同順位ジョブの順序は保証しない。
- 既に実行中のジョブを、優先度によって中断しない。
- リトライ時も元の優先度を維持する。
- 継続して高優先度ジョブが登録される場合の低優先度ジョブの最大待機時間は保証しない。

実行可能なジョブが存在し、実行枠が空いている場合は、新たな登録操作なしに実行を進めること。

## 8. 状態管理

既存の `JobStatus` を使用する。

| 状態 | 意味 |
|---|---|
| `PENDING` | 実行待機・依存関係待機・バックオフ待機 |
| `RUNNING` | ジョブ本体またはその終了処理を実行中 |
| `SUCCEEDED` | ジョブ全体が正常終了 |
| `FAILED` | ジョブ全体が異常終了 |
| `CANCELLED` | ジョブ全体のキャンセルが確定 |

v2.0では、既存の状態遷移に加えて以下を認める。

- `RUNNING → PENDING` はリトライ待機への遷移とする。
- `PENDING → FAILED` は依存関係の不成立による遷移とする。

`SUCCEEDED`、`FAILED`、`CANCELLED` は終端状態とし、確定後は変更しない。

`wait()` はジョブ全体が終端状態になるまで待機する。

`get_result()` はジョブ全体の最終結果のみを返す。リトライ待機中も `JobNotFinishedError` とする。

## 9. キャンセルおよび同時実行数制限との連携

- 既存の `cancel()` の受付結果・重複要求・例外の契約を維持する。
- 実行前、依存関係待機中、バックオフ待機中のジョブをキャンセルできる。
- 実行前にキャンセルが確定した場合、処理本体を開始しない。
- 実行中のキャンセルでは、実際の処理終了結果を優先する。
- タイムアウトおよび明示的キャンセルが競合する場合、先に受け付けた中断要求を優先する。
- 後から発生した中断要求によって同じ実行処理の終了処理を重複して中断しない。
- タイムアウトやキャンセルの通知後も、処理が継続している間は実行枠を保持する。
- 依存関係待機中・バックオフ待機中は実行枠を占有しない。
- 同時実行数制限の上限を超えてジョブ本体を実行してはならない。
- あるジョブのキャンセルや失敗が、依存関係のないジョブを中断してはならない。

## 10. 非機能要件

- 単一プロセス内で動作すること。
- 外部サービスを必須としないこと。
- 非同期の待機処理によってイベントループをブロックしないこと。
- 複数ジョブの実行・完了・キャンセル・リトライが競合しても、公開契約の整合性を維持すること。
- 同一ジョブの処理本体を同時に複数実行しないこと。
- 最終状態および結果をエンジン稼働中に参照できること。
- エンジンインスタンス間でジョブ状態や実行枠が干渉しないこと。
- 既存123ケースの共通契約テストが引き続き合格すること。

## 11. 対象外

- ジョブの永続化・プロセス再起動後の復旧
- 分散実行
- 実行中ジョブの優先度による強制中断
- 優先度の動的変更
- 登録後の依存関係変更
- 動的なDAG構築
- ジョブ間の結果の自動受け渡し
- ジョブ全体の総実行時間制限
- Jitter
- 失敗した試行の副作用のロールバック
- 公開APIによる試行履歴の取得
- Web API・GUI

## 12. 実装上の自由度

内部アーキテクチャ、クラス構成、責務分担、データ構造、スケジューリング方式、Task管理方法およびデザインパターンは指定しない。

実装者は、公開契約を満たすために必要と判断した場合、既存の設計を変更してよい。
