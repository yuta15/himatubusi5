# 非同期ジョブ実行エンジン 仕様書 v1.0

現在の実装は、以下のv1.0仕様に加えて [キャンセル追加仕様 v1.1](cancel.md) に対応する。
キャンセルに関する記述と公開インターフェースの追加はv1.1仕様を優先する。

## 1. 概要

Pythonで動作する非同期ジョブ実行エンジンを開発する。

利用者が任意の非同期Python処理をジョブとして登録し、非同期に実行できることを目的とする。

ジョブの登録、実行状態の確認、実行結果の取得、完了待機を提供する。

## 2. スコープ

### 対象

- ジョブの登録
- ジョブの非同期実行
- ジョブの実行状態管理
- ジョブの実行結果取得
- ジョブの実行失敗の検知
- ジョブの完了待機

### 対象外

- ジョブの永続化
- プロセス再起動後の復旧
- ジョブのキャンセル
- リトライ
- 実行優先度
- 分散実行
- Web APIおよびGUI

## 3. 機能要件

### ジョブ登録

- 利用者は任意の非同期Python処理をジョブとして登録できる。
- ジョブには一意な識別子を割り当てる。
- 登録操作はジョブの完了を待たずに終了する。
- 登録時に処理へ位置引数およびキーワード引数を渡すことができる。
- 同じ処理を複数のジョブとして登録できる。
- 登録対象は、呼び出すとAwaitableを返すCallableとする。

### ジョブ実行

- 登録されたジョブを非同期に実行する。
- 複数のジョブを並行して実行できる。
- ジョブごとに独立して実行状態を管理する。
- あるジョブの失敗によって、他のジョブの実行が中断されない。

### 実行状態管理

ジョブは以下の状態を持つ。

| 状態 | 説明 |
|---|---|
| PENDING | 登録済み・実行待ち |
| RUNNING | 実行中 |
| SUCCEEDED | 正常終了 |
| FAILED | 異常終了 |

状態遷移は以下とする。

- PENDING → RUNNING → SUCCEEDED
- PENDING → RUNNING → FAILED

以下を満たすこと。

- 登録時の初期状態は `PENDING` とする。
- 実行開始時に `RUNNING` に遷移する。
- 処理が正常終了した場合は `SUCCEEDED` に遷移する。
- 処理が例外によって異常終了した場合は `FAILED` に遷移する。
- `SUCCEEDED` および `FAILED` は終端状態とし、変更されない。
- 登録操作が返った時点で、ジョブが `RUNNING` または終端状態に遷移していてもよい。

### 実行結果取得

- 利用者はジョブIDを指定して実行結果を取得できる。
- 正常終了したジョブは、処理の戻り値を取得できる。
- 実行結果の取得操作は、ジョブの完了を待機しない。
- 実行前または実行中のジョブについては、結果が未確定であることを通知する。
- 失敗したジョブについては、失敗したこととその原因を確認できる。
- 処理の戻り値が `None` である場合と、結果が未確定である場合を区別できる。

### ジョブ状態照会

- 利用者はジョブIDを指定して現在の実行状態を取得できる。
- ジョブの状態は実行中も照会できる。
- 存在しないジョブIDを指定した場合は、正常な照会結果と区別できる。

### ジョブ完了待機

- 利用者は指定したジョブの終了を待機できる。
- 完了待機中に他の非同期処理の実行を妨げない。
- 正常終了と異常終了のどちらの場合も待機を終了できる。
- 完了待機操作はジョブの実行結果を返さない。
- 完了済みのジョブに対する待機は速やかに終了する。

## 4. エラー契約

| ケース | 要求される振る舞い |
|---|---|
| 存在しないジョブIDの指定 | `JobNotFoundError` を送出する |
| 未完了ジョブの結果取得 | `JobNotFinishedError` を送出する |
| 失敗したジョブの結果取得 | `JobExecutionError` を送出する |
| ジョブ実行中の例外 | 対象ジョブを `FAILED` にし、元の例外を保持する |
| 他のジョブの失敗 | 実行中の別ジョブへ影響させない |
| 登録対象がCallableでない場合 | `TypeError` を送出し、ジョブを登録しない |

`JobExecutionError.cause` には、ジョブ実行時に発生した元の例外オブジェクトを保持すること。

`wait()` はジョブが正常終了・異常終了した場合のいずれも正常復帰すること。ただし、存在しないジョブIDを指定した場合は `JobNotFoundError` を送出する。

## 5. 非機能要件

### 実行環境

- 単一プロセス内で動作すること。
- 外部サービスへの依存を必須としないこと。

### 並行性

- 複数ジョブを並行実行できること。
- あるジョブが非同期に待機している間、他の実行可能なジョブが進行できること。
- CPU負荷の高い処理の並列高速化は保証対象外とする。

### データ保持

- 登録されたジョブの状態および結果は、エンジンの稼働中に参照できること。
- プロセス終了後のデータ保持は保証しない。

### テスト可能性

- 外部サービスを使用せずに主要機能を検証できること。
- ジョブの成功、失敗、並行実行、状態遷移を検証できること。

## 6. 公開インターフェース

### インターフェース定義

公開インターフェースは `interface.py` に定義する。

実装は同ファイルに定義された以下の契約を満たすこと。

- `JobEngine`
- `JobStatus`
- `JobError` および派生例外

`interface.py` の定義は変更してはならない。

実装クラスが `JobEngine` を直接継承する必要はない。ただし、定義されたメソッドの引数、戻り値、振る舞いを満たすこと。

### エントリーポイント

`main.py` に定義された `create_engine()` を実装のエントリーポイントとする。

- 関数名、引数、戻り値の契約を変更しないこと。
- 関数内部の実装は自由に変更してよい。
- 呼び出しごとに独立したジョブ実行エンジンを生成すること。
- 生成したエンジンは `JobEngine` の契約を満たすこと。

### 公開APIの動作

- `submit()`：ジョブを登録し、一意なジョブIDを返す。ジョブの完了は待機しない。
- `get_status()`：指定したジョブの現在の状態を返す。
- `wait()`：指定したジョブが終端状態になるまで非同期に待機する。
- `get_result()`：正常終了したジョブの戻り値を返す。未完了ジョブについては待機せず例外を送出する。

すべてのメソッドは `interface.py` に定義された非同期インターフェースに従うこと。

## 7. 受け入れ条件

以下の条件をすべて満たすこと。

- [ ] 引数を受け取るジョブを登録できる。
- [ ] 登録操作がジョブの終了を待たずに完了する。
- [ ] 複数ジョブを並行して実行できる。
- [ ] ジョブの状態が定義された順序で遷移する。
- [ ] 正常終了したジョブの戻り値を取得できる。
- [ ] `None` の戻り値と未完了状態を区別できる。
- [ ] ジョブ実行中に発生した例外を確認できる。
- [ ] あるジョブの失敗が別のジョブへ影響しない。
- [ ] ジョブIDを指定して状態を照会できる。
- [ ] ジョブの完了を非同期に待機できる。
- [ ] 存在しないジョブIDを適切に扱える。
- [ ] `create_engine()` の呼び出しごとに独立したエンジンを生成できる。
- [ ] `interface.py` の公開契約を変更せずに実装できる。

## 8. 実装上の自由度

以下は本仕様では指定しない。

- アーキテクチャ
- 内部のクラスおよび関数構成
- デザインパターン
- 内部データ構造
- ディレクトリ構成（公開契約で指定されたファイルを除く）
- 使用するPython標準ライブラリおよび外部ライブラリ
- ジョブのスケジューリング方式

上記は実装者が決定するものとする。ただし、本仕様および `interface.py` の公開契約を満たすこと。

別途アーキテクチャや設計に関する資料が与えられた場合は、その資料の制約にも従うこと。

## 9. v1.1の実装設計

既存の `Engine → JobRunner → Job` の構成を維持する。

- `Engine` はIDからジョブとRunnerを検索し、`cancel()` をRunnerへ委譲する。
- `JobRunner` はTaskとキャンセル要求の受付済みフラグを保持する。終端状態への要求や重複要求は `False` を返し、Taskへキャンセルを再通知しない。
- `Job` は状態・結果・完了通知を管理する。`CANCELLED` への遷移は `PENDING` または `RUNNING` からのみ許可し、結果取得時は `JobCancelledError` を送出する。

実行前のTaskはキャンセルされるとRunnerの処理自体が始まらないため、`PENDING` の場合は要求受付時に `CANCELLED` と完了通知を確定する。Callableは呼び出さない。
`RUNNING` の場合は `Task.cancel()` で一度だけ通知し、終了処理も含めた実際の終了を待ってRunnerが状態を確定する。
`CancelledError` が伝播した場合は `CANCELLED`、捕捉後に正常終了した場合は `SUCCEEDED`、別の例外で終了した場合は `FAILED` となる。

要求の判定・受付・通知には途中の `await` がなく、同一イベントループ上で重複受付を防ぐ。
完了待機は既存の `asyncio.Event` を利用するため、待機者のキャンセルは実行Taskや他の待機者へ伝播しない。

開発用依存パッケージを導入したPython 3.14以降の環境で、`python -m pytest -q` により回帰テストとキャンセルのテストを実行できる。
